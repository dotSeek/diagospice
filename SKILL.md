# Diago Spice: Design System Skill

## When to Use

- Building new UI components for Diago Spice.
- Reviewing or updating existing component styles.
- Choosing colors, typography, or spacing for restaurant pages.
- Checking designs against the extracted token set.

## Context

- **Product:** Diago Spice: https://diagospice.co.uk
- **Surface:** restaurant website
- **Audience:** Local diners and families in Swansea
- **Character:** Printed paper menu look in logo red, inspired by the cowboy era of 1865 to 1895, set in a two font system.

## Page Pattern

Layout pattern follows https://damariatemplate.webflow.io/menu. Rebuilt in our own code, with no template images, illustrations or copy.

- Paper sheet on a wallpaper background, inside a 3px red page frame.
- Top bar straddles the frame: red menu circle, logo card, red reserve pill with a phone icon.
- Huge uppercase Playfair word held between hairline rules.
- Section titles in italic uppercase between two diamonds.
- Dish rows: red Playfair name, price at the right, note below.
- Two column rows split by a vertical hairline, then a three column row.
- Double stroke tinted cards with centred content and ink style photo.
- Checkered divider, black square drop cap, inked postmark.
- Solid red blocks with a kicker and rule over a large title.
- Footer box sits across the bottom edge of the frame.

### Logo use

On the site the logo appears only in the top bar card and the footer. On the PDFs it appears only on the cover.

### Icons

All icons are inline shapes, with no icon font. Diamond (11px rounded square, rotated 45 degrees), badge (red rounded square with a white four point star), close cross (15 grid, 3px round stroke), phone handset, Facebook and WhatsApp marks in a 44px red circle. The badge slides in on hover beside site menu and footer links.

### Artwork

Engraved line drawings with hatch shading, shared by the site and PDFs from `src/data/artwork.ts`: telephone, burger, bowl, fries, cake, cloche, tankard, chilli, compass. All are drawn for Diago Spice, so do not paste in template illustrations. Use them in the spare space beside or below a menu category. Ink on paper, or white on the red panel.

### Map

Free and open source: MapLibre GL with OpenFreeMap tiles, no API key or billing. Colours live in `src/data/mapStyle.ts` and follow this palette. Red pin with a white star, paper popup, square red controls, and the attribution must stay visible.

### SEO and sharing

A PDF cannot carry Open Graph tags, so share `/menu/` and `/bar-menu/`, not the PDF links. Those static pages, their 1200 x 630 images in `public/og/` and the sitemap are generated by `npm run menu:pdf`, so rerun it after any menu change.

### Menus

The food menu and the bar menu are separate sections with separate PDFs: `diago-spice-menu.pdf` and `diago-spice-bar-menu.pdf`.

## Constraints

### Always

- Use tokens from the tables above: do not introduce new values.
- Include hover, focus-visible, and disabled states for interactive elements.
- Follow the 8px spacing grid.
- Meet WCAG 2.2 AA contrast minimums.

### Never

- Do not introduce colors outside the extracted palette.
- Do not use arbitrary spacing values: stick to the scale.
- Do not use full-uppercase text for body or paragraph content.
- Do not nest interactive elements (e.g. buttons inside links).
- Do not ship components without defining hover, focus-visible, and disabled states.

## Tone

Concise, confident, implementation-focused. Avoid filler preambles.

## Authoring Workflow

When creating or documenting a component for this system:

1. State intent: one sentence on purpose.
2. Map tokens: list every token the component uses.
3. Define anatomy: named parts with token assignments.
4. Specify states: default, hover, focus-visible, active, disabled, loading, error, empty.
5. Describe interactions: keyboard, pointer, touch, edge cases.
6. Add a11y criteria: testable pass/fail checks.
7. List anti-patterns: concrete misuse examples.
8. Close with the Definition of Done checklist.

## Output Structure

Component guidelines must contain, in order:

1. Overview (purpose, when to use, when not to use)
2. Tokens and foundations
3. Anatomy, variants, responsive behavior
4. States and interactions
5. Accessibility (ARIA, contrast, focus, screen reader)
6. Content guidelines (copy rules, tone)
7. Anti-patterns with reasoning

## Component Requirements

- Reference only tokens from the tables above.
- Define all states: default, hover, focus-visible, active, disabled, loading, error.
- Handle edge cases: empty, overflow, truncation, max content.
- Include keyboard navigation behavior.
- Document ARIA roles and labels.

## Definition of Done

- Default state renders (smoke test).
- All states visually verified.
- Zero hardcoded visual values: tokens only.
- Keyboard navigation works without pointer.
- No critical a11y violations.
- Tested at min and max breakpoint.
- At least one anti-pattern documented.
- Purpose, usage, and limitations documented.
